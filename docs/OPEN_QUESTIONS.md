# OPEN_QUESTIONS.md — Ambiguities, unspecified details, and prototype decisions

Each item: what the paper says (if anything), status, and the **[PROTOTYPE]** decision we take (reversible unless marked otherwise). Nothing here is presented as a paper requirement.

| # | Question | Paper status | Prototype decision |
|---|---|---|---|
| OQ-1 | Threshold **τ** for "short reply" (DRAM) vs "long reply" (SSD) | Symbol only; no value. Also appears with two unit readings: "prior output length < τ tokens" (Table 2, citing [12]) and "expected reuse distance exceeds τ tokens" (§3.2 prose). §2.2 measures reuse distance in *intervening requests*, not tokens. | Configurable `tau_tokens`, default **4,096 tokens** reply length (≈1 MiB FP8 KV at 7.5 KiB/token/rank — matches "small footprint" DRAM-bound intent). The two readings are recorded as a paper inconsistency; we implement the *reply length* reading (Table 2 is the operative signal table). |
| OQ-2 | Threshold **L_agent** for agentic/long sessions | Symbol only; no value. | Configurable `l_agent_tokens`, default **65,536 tokens** (Claude Code median request = 0.52 GiB/rank ≈ 218K tokens ⇒ well above; keeps "small-footprint" scopes in DRAM). |
| OQ-3 | Block size for the prototype | Traces use native 512 (Mooncake), 16 (Qwen), 64 (Claude Code) tokens; engine pages are 256 tokens. Trace replay uses each trace's native size. | Configurable; default **256 tokens** (matches the implemented engine's page size and our synthetic workloads). Synthetic traces may also use 64 to mimic Claude Code granularity. |
| OQ-4 | When is HRRN priority recomputed? | Eq. 1 given; ordering "pending prefetches" implies evaluation at dispatch-decision time; no statement about continuous reordering. | Recompute priority **at each dispatch decision** over pending SSD-Preparing requests (lazy evaluation, no background resort). Documented as reference interpretation. |
| OQ-5 | Role of Fig. 5(c)(i) "SSD restore + promotion" inside FlatCake | Figure depicts three restore paths; §3.2 argues SSD-resident reusable blocks need no promotion; FlatCake's path is (iii) GDS streaming; (ii) DRAM restore serves DRAM-pinned scopes. | FlatCake implements (ii) DRAM dispatch + (iii) direct-read path. Promotion (i) is treated as a **baseline mechanism** (tiered behavior), not FlatCake behavior. |
| OQ-6 | "DRAM full → SSD" spill: what exactly triggers it, and is spilled data reclaimable as one-shot? | Table 2 row 4: "Turn = 1 or DRAM full → SSD". No spill-back policy. | Once placed on SSD, never migrated back (write-once invariant). DRAM-full = DRAM pool allocation failure at write time. |
| OQ-7 | Block key construction: how (session ID, layer, token range) is formed | Key tuple given; ID format/token-range granularity unspecified. | `key = (session_id: u64, layer: u32, token_start: u64)` with fixed block size; token range derivable from block index. Documented format. |
| OQ-8 | Refcount semantics for shared prompts (global radix-tree refcount > 1) | Refcount = number of sessions referencing the prefix; radix-tree mechanism assumed from SGLang. | Prototype: per-prefix-group refcount maintained by workload/engine (`refcount > 1 ⇒ DRAM`). Synthetic workloads tag shared prompts explicitly. |
| OQ-9 | Index durability / crash recovery | Not discussed (GPU Files are pre-allocated; index is DRAM-resident). | Prototype: rebuild Level-1 index from on-disk descriptor log at startup (format-versioned). Paper makes no claim; our addition is documented as an engineering requirement. |
| OQ-10 | Multi-node coordinator protocol | "Lightweight coordinator tracks aggregate DRAM and SSD capacity" — no protocol given. | **Out of scope** (single node; NodeID=0 always). Reserved bit field implemented per paper. |
| OQ-11 | GPU File (scope file) size / NVMe File Pool sizing | "fixed-size single-extent files"; size unspecified. | Configurable `gpu_file_bytes`, default 256 MiB; sessions larger than one file chain multiple files contiguously (**prototype extension, documented** — paper implies one file per scope but gives no size bound for multi-GiB sessions). |
| OQ-12 | Reclamation watermark values | "high watermark" only. | Configurable `ssd_high_watermark`, default 0.9; reclaim oldest unreferenced extents until ≤ 0.7 (low watermark). |
| OQ-13 | Is DRAM-Ready dispatch per-request or batched? | Figure 3 shows a Ready Queue dispatching to GPU; no batching statement. | Per-request dispatch in the prototype (matches model of Fig. 4); batching left to the serving layer. |
| OQ-14 | Hybrid request semantics: which medium's latency counts | "classify the request by its slowest required medium" — SSD if *any* block is SSD-resident; DRAM blocks pinned. | Implemented exactly as stated; max-GVA comparison per request. |
| OQ-15 | `wait_time_i` units in Eq. 1 | Not stated explicitly (time; KV_size in bytes or KV-transfer volume). | `wait_time` in **seconds** (float), `KV_size` in **MiB** → priority dimensionless and scale-stable on our hardware. Units recorded in code + BENCHMARK_METHODOLOGY. |
| OQ-16 | Level-1 index collision policy | Open-addressed hash, 64-bit CAS; load factor/resizing unspecified. | Open addressing, linear probing, CAS insert, resize at 0.7 load; documented as engineering choice. |
| OQ-17 | What "delivered cache hit rate" counts precisely | "counting only blocks transferred to GPU HBM before prefill". | Hit = block found in cache (HBM-equivalent + DRAM + SSD) and *delivered* to consumer before compute; recompute of a cached-but-undelivered block counts as miss. Matches paper's intent; exact SGLang accounting not reproducible at Level B. |
| OQ-18 | Trace `claude-code-weka-0621` availability/licensing | HuggingFace dataset [33]; not verified in this environment. | **Do not download** (16 GB machine + license unverified). Synthetic workloads only; no claim of production-trace fidelity. |

**Unresolved-by-design:** GPU/CUDA/GDS/cuFile specifics (Fig. 3 data path, §4 GPU staging window) are documented in `FUTURE_GDS_INTEGRATION.md`, not implemented at Level B.
