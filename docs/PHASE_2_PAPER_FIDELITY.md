## 1. Mechanism-level verification (briefing items a–j)

### (a) GVA bit layout and the 2^60 partition — **FAITHFUL**
Paper (p. 5–6): "MediaType [63:60] (4 bits: 0=DRAM, 1=SSD, with reserved encodings for future media), NodeID [59:48] (12 bits, up to 4,096 nodes), and Offset [47:0] (48-bit byte offset, up to 256 TiB per node)"; "GVA < 2^60 for DRAM vs. GVA ≥ 2^60 for SSD".

- Encode `media << 60 | node << 48 | offset` with guards media ≤ 1, node ≤ 0xFFF, offset ≤ 2^48−1 — `src/types.rs:22-27`.
- Field extraction via bit masks — `src/types.rs:28-36`; classification `self.0 >= 1 << 60` — `src/types.rs:38-40`.
- DRAM GVA = node 0 + arena byte offset (`src/engine.rs:309` `Gva::encode(0, 0, off)`); SSD GVA packs `(file_seq << 28) | in_file_off` (`src/cio/layout.rs:377`, resolve inverse `src/cio/layout.rs:402-410`).
- Boundary/invalid-value tests: `tests/gva_tests.rs:167-204` (t1_*), plus `src/main.rs:9-24` selftest.

Deviation (micro, documented): the paper says MediaType encodings ≥ 2 are "reserved"; the prototype treats them as **invalid** (`types.rs:23` returns None). Conservative and consistent with the T1 test plan; a future media could not be added without touching the guard. Also: the SSD *offset packing* (`file_seq[47:28] | in_file_off[27:0]`, `types.rs:15-18`) is a prototype scheme the paper does not specify — it preserves the paper's invariant that Offset is a node-relative byte offset and keeps the 2^60 partition exact. Documented in ARCHITECTURE §6.

### (b) Write-once publish-after-write (§3.2) — **FAITHFUL** (one engine-path defect, see §5.1)
Paper (p. 5): "FC-GVA allocates a block's GVA before asynchronous write submission but publishes the key-to-GVA entry into the Level 1 index only after the DMA or GDS write callback completes."

- Index states EMPTY/PENDING/PUBLISHED/TOMBSTONE (D13) — `src/gva/index.rs:55-58`.
- `insert_pending` claims PENDING before any write — `src/gva/index.rs:102-134`; `publish` stores the GVA (Release) then flips PENDING→PUBLISHED (Release CAS) — `src/gva/index.rs:144-153`; readers never observe PUBLISHED with a stale GVA (`lookup` re-checks state after loading GVA, Acquire) — `src/gva/index.rs:207-244`.
- Engine: SSD put reserves **all** index slots before the batch write and publishes only after `append_scope_batch` returns GVAs — `src/engine.rs:334-379` (comment "Reserve index slots BEFORE the write; publish after (T3)" at :334). Failure paths roll back PENDING→TOMBSTONE — `src/engine.rs:351-360, 405-409`.
- Racing get during in-flight put → Miss or Pending, counted separately as `pending_racing_gets`, both treated as miss by design (D16/ARCHITECTURE §8) — `src/engine.rs:449-455`; cross-thread test `tests/gva_tests.rs:382-424` (t2_index_pending_invisible_until_publish_cross_thread), `tests/gva_tests.rs:425-447` (t3_*).
- Write-once immutability: a re-put of a published key returns the existing slot and `publish` refuses non-PENDING slots — `src/gva/index.rs:99-101, 144-148`; the already-published GVA can never be clobbered.

**Defect in the DRAM-spill path only** (engine, in-flight): when the arena is full the slot is rolled back and the block is appended to SSD with `slot = None`, which publishes **nothing** (`src/engine.rs:314-325` → `src/engine.rs:240-265`, publish guarded by `if let (Some(s), …)` at :252). The paper's protocol requires publishing after the write completes; here the write completes but the entry is never published → the block is permanently invisible, every future get misses and `recompute_persist` appends a duplicate copy (leaked extent until scope reclaim; hit-rate and write-amp distortion in spill-heavy runs). This is a correctness bug, not a documented interpretation — see §5.1.

### (c) Table-2 placement signals + OQ-19 precedence — **ADAPTED, defensible; two sub-orderings are genuine judgment calls**
Paper Table 2 (p. 5), verified verbatim:

| Reuse scope | Write-time signal | Medium |
|---|---|---|
| Shared prompt | Prefix refcount>1 | DRAM (m=0) |
| Short-turn chat | Turn>1, prior reply<τ | DRAM (m=0) |
| Agentic / Long | Context≥L_agent or reply≥τ | SSD (m=1) |
| One-shot / Spill | Turn=1 or DRAM full | SSD (m=1) |

Implementation (frozen D14/OQ-19, ARCHITECTURE §4): sticky-SSD short-circuit, then refcount>1→DRAM, ctx≥L_agent→SSD, reply≥τ→SSD, turn==1→SSD, turn>1∧reply<τ→DRAM — `src/gva/placement.rs:28-55`. τ=4096 / L_agent=65536 configurable (OQ-1/2, D5) — `src/config.rs:56-57`. DRAM-full spill handled at the engine as Table-2 row 4's "or DRAM full" (arena reserve failure → SSD + scope flip, OQ-6) — `src/engine.rs:314-318`, flip `src/gva/reclaim.rs:194-203`, metric `dram_spill_puts` — `src/engine.rs:318`. Per-row tests: `tests/gva_tests.rs:469-574` (t4_row1..row5, t4_dram_full_spill_flips_scope_to_ssd_oq6).

Defensibility assessment:
- **Stickiness conflict** (short-chat row vs turn=1 one-shot under appends) is real in the paper: Table 2 row 2 cannot fire for a scope created at turn 1 (row 4 fires first) if scope medium is fixed at creation — yet §3.2 (p. 5) explicitly says appends "bind the newly generated blocks to the same session scope so the session's history remains grouped on its assigned medium." Keeping SSD scopes sticky is therefore the *paper-supported* reading; splitting a session across media would break the §3.4 contiguity invariant that the whole FC-CIO design rests on. The implementation additionally lets DRAM-scope appends re-evaluate rows fresh (so row 2 does fire for late-first-put/unshared-DRAM sessions; `src/gva/placement.rs:12-17`, engine `scope_medium` flip path `src/engine.rs:133-143`) — this is the documented reference interpretation (OQ-19/OQ-20), explicitly flagged as such. Defensible.
- **Shared ∧ long-context** (refcount>1 ∧ ctx≥L_agent): implementation pins it DRAM (row 1 first), matching the paper's row listing order. The opposite resolution (long→SSD first) would also be paper-consistent since Table 2 has no priority. Judgment call — see Risk R1.
- The τ unit inconsistency the paper itself carries ("prior output length < τ tokens" in Table 2 vs "expected reuse distance exceeds τ tokens" in §3.2 prose, p. 5) is resolved to the Table-2 reading (reply_tokens) — OQ-1, recorded.

### (d) Session-granularity reclamation, reader/writer refs, tombstone-first (D15) — **ADAPTED (strengthened beyond paper; drain-to-low is a documented deviation)**
Paper (p. 6): "tracks active readers per session scope with an atomic reference count; when SSD utilization crosses a high watermark, FlatCake reclaims the oldest unreferenced session extents by returning their pre-allocated GPU Files to the free pool in O(1) metadata operations."

- Oldest-unreferenced selection by `(creation_ts_us, session)`, only scopes with zero reader AND zero writer refs — `src/gva/reclaim.rs:283-302`.
- Tombstone-invalidate index entries **before** any extent free (kills stale-GVA wrong-data hits) — `src/gva/reclaim.rs:305-324`; test spy-asserts order `tests/gva_tests.rs:659-687` (t6_reclaim_tombstones_index_before_freeing_extents).
- O(1) metadata-only free, zero payload ops: DRAM free-list insert/coalesce `src/gva/arena.rs:126-165`; SSD per-file free-list push + counter `src/cio/layout.rs:415-442`; `reclaim_payload_ops` stays 0 (asserted in `tests/engine_tests.rs:166`).
- Reader refs pinned **at resolution time, before index lookup**, held to request end — `src/engine.rs:428, 575` (contract documented `src/gva/reclaim.rs:152-163`); writer refs held from pin to publish — `src/engine.rs:284-285, 412` (D15: a PENDING write pins its scope). The registry lock is held across select→tombstone→free→remove, making the ref-check atomic — `src/gva/reclaim.rs:279-283`.
- Watermark: trigger `usage > high × capacity`, SSD usage = logical bytes written, capacity = pool × file bytes — `src/gva/reclaim.rs:260-274`, engine trigger `src/engine.rs:161-201`. Advisory when nothing is reclaimable — `src/gva/reclaim.rs:300-302`.

Deviations (both documented, both defensible):
1. **Writer refs** (D15) are not in the paper (paper counts "active readers" only). This is a strengthening that closes the in-flight-writer-into-freed-extent race; it cannot weaken paper semantics.
2. **Drain-to-LOW watermark** (D22, OQ-12): the paper states only a high-watermark trigger; the implementation keeps freeing until usage ≤ low watermark (`src/gva/reclaim.rs:278`). A literal while>high reading would stop in the [low, high) band after one free. Deviation recorded in DECISIONS D22.
3. Granularity: the paper returns "pre-allocated GPU Files to the free pool" (whole files); the implementation frees per-extent and recycles a file only when `freed == appended` (`src/cio/layout.rs:437-439`). Under the enforced 1-file-per-scope discipline (OQ-11/D20, `src/cio/layout.rs:291-309` hard error on overflow) this is equivalent for whole-scope reclaim.
4. Refcounts are atomics but all access is serialized under the registry Mutex (`src/gva/reclaim.rs:219-230`) — stronger than the paper's plain atomic refcount; semantics equivalent.

Gap found (engine, in-flight): the reader pin covers only `spec.signals.session` — hybrid requests also read the **shared-prompt session's** blocks (e.g. session 1), whose scope is *not* pinned; reclaim of that scope between lookup and arena read can free a resolved GVA's extent. See §5.2.

### (e) HRRN Eq. 1 semantics (OQ-4/15) — **FAITHFUL formula; units are the documented risk**
Paper Eq. 1 (p. 6, verified verbatim): `Priority_i = 1 + wait_time_i / KV_size_i`; "Smaller SSD restores receive higher initial priority… wait_time_i grows linearly with waiting time so multi-gigabyte restores are guaranteed eventual dispatch."

- Formula exact: `1.0 + wait_s / size_mib` — `src/mas/scheduler.rs:54-57` (in-flight file).
- Recomputed lazily at each dispatch decision via O(n) argmax scan, ties FIFO by insertion order (OQ-4 reference interpretation) — `src/mas/scheduler.rs:255-286`.
- KV_size = the SSD portion's transfer volume (`req.size_bytes` set at enqueue — `src/engine.rs:500-507`), matching the paper's "substitutes SSD KV transfer volume for service time".
- Zero-size guard → treated as 1 MiB (no division by zero) — `src/mas/scheduler.rs:55`; tested `tests/mas_tests.rs:176-188`.
- Behavior tests: small-first then giant-overtakes-by-aging — `tests/mas_tests.rs:153-175` (t8_hrrn_small_first_then_giant_aging_overtakes); starvation tests `tests/mas_tests.rs:212-266`.

Note: ordering by `wait/KV_size` is invariant to linear unit choices (µs vs s, bytes vs MiB), but the relative weight of the additive `1` is **not** — with KV_size in raw bytes the aging term would be negligible and HRRN would degenerate toward FIFO. The OQ-15 choice (wait in seconds, size in MiB) is what makes the paper's "guaranteed eventual dispatch" observable on prototype timescales; it is a genuine judgment call — Risk R2.

### (f) arrival_ts re-admission (§3.3) — **FAITHFUL**
Paper (p. 6–7): "Rather than appending the promoted request to the tail of the DRAM-Ready Queue, FC-MAS inserts it ordered by its original arrival timestamp (arrival_ts). Because the time spent in SSD prefetching already counts toward its queue seniority, the promoted request is dispatched ahead of newly arriving DRAM hits."

- Re-admit keyed by original `arrival_ts_us` with `seq_no`/`enqueued_us` restored from the awaiting table (seniority + total-wait preserved across the prefetch stay) — `src/mas/scheduler.rs:295-316`.
- DRAM-Ready heap ordered by `(arrival_ts_us, seq_no)` — `src/mas/scheduler.rs:96-120, 216`; `pop_dram` returns the minimum — `src/mas/scheduler.rs:222-245`.
- Engine: after FC-CIO completes the prefetch, the ssd_worker re-admits a completion marker with the original arrival_ts and empty blocks; a dram_worker completes the request in arrival order — `src/engine.rs:711-719, 622-653`. Data delivery order follows arrival order exactly as Fig. 4(b) depicts; the prefetch itself is HRRN-ordered (paper-consistent split).
- Wait accounting spans the full stay (first-enqueue stamp preserved) — `src/mas/scheduler.rs:21-26, 209-211`.
- Tests: re-admitted request pops ahead of later DRAM hits; wait covers prefetch — `tests/mas_tests.rs:104-152` (t9_*).

### (g) Layer-major scope layout + sort-merge with 64 KiB gap bridging (§3.4) — **FAITHFUL**
Paper (p. 7–8): GPU File = "one pre-allocated single-extent file in the NVMe File Pool", 1:1 per scope; "Within each turn's write batch, blocks are laid out layer-major … subsequent turns of the same session append new layer-major segments to the same GPU File"; ideal read count O(layers); read-time sort by `(gpu_file_id, offset)`, linear merge, "bridges gaps smaller than a configurable byte threshold (Δgap = 64 KiB)"; merged descriptors striped round-robin across workers with private handles.

- Write path: one pre-allocated `gpu_file_bytes` file per SSD scope (`preallocate_file` `src/cio/layout.rs:116-124`; pool of `gpu_file_pool` files :228-230); per-turn batch appends layer-major segments at 4 KiB-aligned starts, advancing `append_off` per session — `src/cio/layout.rs:257-316` (segment loop :284-290, append pointer :313-314). Layer-major GVA ordering returned to the engine — `src/cio/layout.rs:372-387`.
- Inter-turn/inter-segment padding ≤ 4095 B < Δgap ⇒ absorbed by bridging (T13 bound holds by construction) — ARCHITECTURE §6, `src/cio/layout.rs:287`.
- Read path: descriptors resolved per GVA (`src/engine.rs:675-679`), sorted by `(file_seq, in_file_off)`, linear merge of adjacent/overlapping ranges, gaps ≤ `gap_bridge_bytes` (default 65536, `src/config.rs:58`) bridged with over-read accounting, never crossing files — `src/cio/coalesce.rs:50-108`. Bridged bytes are read but mapped to **no** descriptor, so reconstruction is exact — `src/cio/coalesce.rs:6-11, 83-91`; per-descriptor `part_lens` (D23) — `src/cio/coalesce.rs:26-35`.
- Tests: `tests/cio_tests.rs:299-501` (t12_adjacent/overlap/gap_not_bridged/gap_bridged/no_merge_across_files/shuffled/duplicates/zero-threshold/reconstruction-with-sentinels), `tests/cio_tests.rs:94-247` (t11 round-trip incl. padding and session-size guard), O(layers)-ops bound `tests/cio_tests.rs:503-542` (t13_read_ops_bounded_full_restore).
- Micro-deviation: the paper says "gaps **smaller than** Δgap"; the implementation bridges `gap <= Δgap` (`src/cio/coalesce.rs:82`) — a boundary-inclusive off-by-one at exactly 64 KiB. Immaterial; noted for precision.
- Round-robin striping across workers: the engine's N `ssd_workers` each own a private `Reader` (private NO_BUFFERING handles per file, `src/cio/stream.rs:41-72`); requests are striped across workers by the scheduler's HRRN picks rather than per-merged-range round-robin — the Level-B control-plane equivalent; per-worker handles match the paper's "private cuFileHandle" requirement. GDS batch submission itself is Level C (§6).

### (h) Bounded per-worker windows, wait-not-abort on saturation (§3.4) — **FAITHFUL (window size is a code constant, documented)**
Paper (p. 8): "streaming coalesced layer extents via GDS into a small, double-buffered GPU HBM staging window (sized to two transformer layers per active stream) … bounds staging memory to a constant O(1) HBM window per GPU. When concurrent restores saturate the window under heavy load, incoming prefetches wait on CUDA stream events rather than revoking in-flight prefetches and recomputing cached tokens."

- Exactly two window buffers per worker, cycled ping-pong; the next chunk is prefetched on a scoped thread while the current chunk is scattered — the Level-B analog of the paper's I/O-stream/compute-stream overlap — `src/cio/stream.rs:41-48, 155-224`.
- Memory per worker O(window_bytes) regardless of request size; chunk step rounded down to 4 KiB (D24) — `src/cio/stream.rs:33-39`; padded tails and bridged bytes never delivered — `src/cio/stream.rs:209-220`.
- Window = `SSD_WINDOW_BYTES = 8 MiB` code constant — `src/engine.rs:46-50`. The paper sizes the window to two layer extents; 8 MiB ≈ 2 layer extents at typical densities and is bounded O(1) regardless — documented deviation (A2 also flags non-configurability; harmless).
- No revoke-on-saturation: there is no abort path anywhere on the FlatCake SSD read path; backpressure is *waiting* — scheduler `enqueue` blocks on the condvar while the queue is at `queue_cap` (`src/mas/scheduler.rs:198-220`), the request's caller waits on its slot condvar (`src/engine.rs:517-525`), and a bounded 200 ms wait-timeout at shutdown reconciles undelivered blocks as recompute instead of dropping them (`src/engine.rs:521-551`). Contrast with the baseline, where staging exhaustion *aborts* and recomputes (`src/baseline.rs:533-549, 652-658`) — the exact mechanism distinction the paper makes (p. 10).
- No DRAM pre-staging on the SSD hit path (T10): SSD reads stream directly from NO_BUFFERING handles into the worker window and then into caller-provided sinks; the DRAM arena is written only by put/recompute-persist, never by the restore path — `src/engine.rs:659-723` vs put path :273-414. `mem_used` = arena + hbm only — `src/engine.rs:602-604`.

### (i) Baseline fidelity (Observations 1 & 2) — **FAITHFUL to the criticized mechanisms; two nuances, neither artificially favorable to FlatCake in mechanism, one slightly weakens the baseline**
Paper mechanisms criticized and their baseline implementations:

| Paper criticism (verbatim source) | Baseline implementation | Evidence |
|---|---|---|
| "newly generated KV blocks are admitted into host DRAM first, evicted incrementally … under LRU" (p. 3) | Every put block inserted into DRAM LRU first; eviction produces spill writes | `src/baseline.rs:451-463` (put), `src/baseline.rs:117-148` (LRU insert/evict), `src/baseline.rs:359-383` (spill) |
| SSD populated "in eviction or FIFO-bucket order rather than session order" (p. 2, p. 6) | Evicted blocks appended at the current bucket cursor — placement order = eviction order, interleaving sessions | `src/baseline.rs:209-227` (write_block), `src/baseline.rs:359-377` |
| "recycle buckets in FIFO order … evicting a single bucket slices across k distinct sessions" (p. 6) | When all buckets are full, the FIFO-next bucket is reclaimed whole; **every** block in it is invalidated regardless of session | `src/baseline.rs:229-260` (advance_or_reclaim); test `tests/baseline_tests.rs:160+` (fifo_bucket_reclaim_invalidates_across_sessions) |
| "concurrent restores contend for bounded staging memory, delaying or aborting prefetches … SGLang revokes the blocked prefetch and falls back to recomputing" (p. 4, p. 10) | Bounded staging pool with bounded wait (100 ms × 2 retries); exhaustion → abort → recompute + re-persist for the whole SSD portion of the request | `src/baseline.rs:283-323` (StagingPool), `src/baseline.rs:530-549` (reserve-or-abort), `src/baseline.rs:387-436` (recompute_one: modeled cost + re-persist + write-amp); test `tests/baseline_tests.rs:120+` (staging_exhaustion_aborts_and_recomputes) |
| Mooncake "promoted into the DRAM tier" (p. 9) | Restored SSD blocks re-inserted into DRAM LRU (churn → more eviction writes) | `src/baseline.rs:637-651` |
| "restoring a scattered prefix issues O(layers×blocks) small reads" (p. 4) | No coalescing: one physical read per SSD block | `src/baseline.rs:606-618` |

Fairness (not weakened): identical hbm-window budget and policy for both systems (D18 — `src/baseline.rs:342` vs `src/engine.rs:90`, same `HbmWindow` type `src/hbm.rs`), identical DRAM budget, identical block/payload model, NO_BUFFERING on both systems' SSD files (D12 — `src/baseline.rs:23, 186-192`), identical recompute cost constant (`recompute_us_per_token`, `src/baseline.rs:398` vs `src/engine.rs:467-468`), identical integrity checking (`src/replay.rs:105-116`). The staging pool (128 MiB) is baseline-mechanism-specific and declared in the parity table (ARCHITECTURE §12) — the paper's own accounting says tiered staging demand scales O(context×concurrency) even with chunked pipelining (p. 4), so the budget is a paper-supported parameter.

Nuance 1 (Risk R3): the baseline reserves staging for the **entire** SSD portion of a request up front (`src/baseline.rs:530-543`) instead of the chunked-pipelined staging the paper describes for tiered systems (p. 4: "Even when chunked pipelining overlaps…"). Same asymptotics O(context×concurrency), but a chunked baseline would hold a smaller instantaneous reservation and abort less often. This can make the baseline's collapse *earlier* than a faithful chunked implementation. What would bound it: compare abort rates against the paper's qualitative claim (Mooncake hit-rate collapse between 0.25 and 0.5 QPS) in a sizing-sweep run.

Nuance 2: the baseline invalidates hbm-window entries when blocks are **spilled DRAM→SSD** and when a bucket is reclaimed (`src/baseline.rs:378-381, 425-428, 472-475`). Strict tier semantics would leave L1 (HBM) copies alone when lower tiers churn; a block both HBM-resident and SSD-reclaimed should still be an HBM hit. This slightly weakens baseline HBM attribution in churn-heavy runs (shifts hits to SSD/recompute). Integrity is unaffected (payloads are deterministic). See Risk R4.

### (j) Open-loop replay + cold-start protocol (§5.1) — **FAITHFUL (synthetic trace is the documented Level-B delta)**
Paper (p. 9): "Requests are replayed in recorded arrival order across arrival rates from 0.1 to 1.0 QPS without cache warm-up." Metrics include delivered hit rate ("counting only blocks transferred to GPU HBM before prefill", p. 9), amplifications, latencies.

- Open-loop driver: each record fires at wall-clock `t0 + ts_us × time_scale` — `src/replay.rs:139-145`; QPS encoded in generated `ts_us` (`src/workload.rs:441-443`); `time_scale` config (`src/config.rs:67`).
- In-flight cap = `queue_cap`; the issue thread **blocks** when saturated and `arrival_ts_us` stays the *intended* ts, so measured latency includes queue wait (honest TTFT analog; D11) — `src/replay.rs:129-137, 199`, scheduler-side backpressure `src/mas/scheduler.rs:198-220`.
- Cold start: no warm-up, no pre-population; measurement window = the full run (ARCHITECTURE §9).
- Delivered-hit accounting per block (hbm/dram/ssd delivered vs miss; OQ-17) — `src/types.rs:159-169`, engine counters `src/engine.rs:437, 487, 555-571`; CSV window rows per pinned schema — `src/replay.rs:264-302`.
- Hybrid requests (DRAM-pinned shared prompt + SSD-resident history) generated explicitly (`shared_with`, OQ-14) — `src/workload.rs:244-257`, assembled at replay `src/replay.rs:167-185`.
- Beyond the paper (prototype necessity, supports all correctness claims): every delivered block's bytes are verified against the frozen deterministic payload (SplitMix64(seed ^ FNV1a(session, layer, token_start))) — `src/replay.rs:105-116`, `src/util.rs:13-44`; failures counted in the results JSON — `src/replay.rs:77, 240, 247`.

Level-B deltas (documented, not fidelity gaps): synthetic regimes replace the production trace (D3/OQ-18 — `src/workload.rs:184-456`), uniform inter-arrivals replace recorded arrivals, no SGLang/LLM (T24).

## 3. (1) Ranked fidelity RISKS — interpretations that could be wrong, and what would prove it

**R1 — Table-2 precedence, specifically shared∧long-context and the near-death of the short-chat row (OQ-19/D14).** The frozen order (refcount>1 first, `src/gva/placement.rs:33-35`) pins a large *shared* prefix in DRAM even at ≥L_agent tokens; and because scope medium is fixed at creation with SSD stickiness, essentially **every non-shared session lands on SSD at turn 1** (`turn==1 → SSD`, `:45-48`) and the paper's "Short-turn chat → DRAM" row only fires for scopes whose first put occurs after turn 1. If the authors instead intended per-turn re-evaluation with scope *splitting*, DRAM would serve far more of the small-session traffic. *What would prove it:* the paper's E2 attribution — Host DRAM supplies a steady **8.0–11.7%** of delivered hits (p. 10). If the prototype's steady-state DRAM hit share lands far below that band on the agentic regime (where shared prompts exist), the precedence reading is suspect; a sensitivity run with "re-evaluate rows fresh on every append (no SSD stickiness)" quantifies the delta. Note the current implementation cannot hit the paper's DRAM band with sessions ≫ shared blocks, so this risk is *likely to materialize* and should be measured at M9, not assumed away.

**R2 — Eq. 1 units (OQ-15).** `wait_s / size_MiB` makes aging observable; `wait_s / size_bytes` (a literal reading of "KV transfer volume") makes the aging term vanish and HRRN degenerate to FIFO. The paper's intent (HRRN [5] substitutes *service time*) suggests the authors may have effectively used `KV_size / bandwidth` (a time), which is proportionally the MiB-scale reading — the implementation's choice is the defensible one, but it is a choice. *What would prove it:* the paper's FC-MAS ablation (mean TTFT −10–11%, P99 −27%, p. 11). Run the planned FC-MAS-off ablation under both unit conventions; if the P99 improvement only appears with the MiB convention, the current reading is validated; if both work, the risk is moot.

**R3 — Baseline staging is stricter than the paper's chunked-pipelined tiered system.** The baseline reserves the entire SSD portion of each in-flight hit up front (`src/baseline.rs:530-543`); the paper (p. 4) describes tiered systems as pipelining SSD→DRAM→GPU in chunks while still holding per-prefix buffers (O(context×concurrency)). Same asymptotics, larger instantaneous reservation → aborts (and the resulting hit-rate collapse) can occur *earlier* than a faithful chunked baseline. *What would prove it:* a staging-sweep run comparing abort-rate/load curves against the paper's qualitative Mooncake collapse onset (between 0.25 and 0.5 QPS, p. 10); if the prototype baseline collapses far earlier than that pattern at equivalent utilization, add chunked pipelining before any comparative claim.

**R4 — Baseline hbm invalidation on spill/bucket-reclaim slightly weakens baseline HBM attribution.** `src/baseline.rs:378-381, 425-428, 472-475` remove delivered-block copies from the hbm window when DRAM eviction or bucket recycling churns lower tiers. Strict tier semantics keep L1 copies untouched by lower-tier events (FlatCake's reclaim correctly leaves the window alone — `src/gva/reclaim.rs` has no hbm interaction). In reclaim-heavy runs this shifts baseline hits from hbm to SSD/recompute. Small, but it biases exactly the E2-style attribution the benchmarks will report. *What would prove it:* remove the spill-path invalidations in a scratch experiment (keeping the bucket-reclaim one, which has a defensible integrity rationale) and measure the hbm-share delta; if negligible, close as no-op.

**R5 — Hybrid DRAM delivery counts.** The implementation delivers the hybrid request's DRAM portion inline and counts each block `hit_dram` (`src/engine.rs:480-489`), while the paper says DRAM-resident prefix blocks are "pinned in place" without specifying whether the pin itself counts as a delivered hit before full-request dispatch. Either reading is defensible; the alternative (attribute those blocks only at completion) changes per-medium attribution, not totals. *What would prove it:* nothing in the paper decides it; record the choice in BENCHMARK_METHODOLOGY before M9 so the E2-analog breakdown is interpretable (already implied by ARCHITECTURE §7; keep it).

**R6 — Pending-get = miss + recompute + re-persist (D16).** Under the open-loop driver, a get can race an in-flight put for the same prefix (agentic turns). The implementation counts it a miss, regenerates, and **re-persists a second copy** (`src/engine.rs:449-455, 465-474`) — the paper never discusses racing gets, and its publish-after-write rationale implies the serving layer would not issue such a get. The re-persist is what inflates duplicate extents when combined with §5.1's spill defect. *What would prove it:* count `pending_racing_gets` per run; if it is material, the trace's put/get ordering (not the engine) should be tightened so a turn's gets strictly follow its put, matching the paper's causal request stream.

**R7 — SSD pool growth beyond the pre-allocated pool.** When the advisory watermark cannot reclaim (`src/gva/reclaim.rs:300-302`), `alloc_file` creates files **beyond** `gpu_file_pool` on demand (`src/cio/layout.rs:196-203`), while the watermark's capacity denominator stays `gpu_file_pool × gpu_file_bytes` (`src/engine.rs:177-179`). The paper's NVMe File Pool is pre-allocated and fixed. Bounded in practice by the generator's SSD-budget guard (`src/workload.rs:200-214`), but an adversarial config could grow SSD beyond the "budget" silently. *What would prove it:* assert-or-log when `next_seq > gpu_file_pool` during a run; if it never fires under the M9 workloads, the deviation is dormant.

## 4. (2) Where the code does something the paper does NOT support

1. **DRAM-spill blocks are never published (engine defect, in-flight file).** `src/engine.rs:314-325` rolls back the PENDING slot and calls `append_one_ssd(..., None, ...)`; `append_one_ssd` publishes only when `slot` is `Some` (`src/engine.rs:240-265`, guard at :252). The block is physically written to its SSD scope but no key→GVA entry ever exists: paper §3.2's protocol (publish after write completion) is violated on this path. Every subsequent get of such a block misses, recomputes, and `recompute_persist` appends a *second* copy (`src/engine.rs:204-237`), leaking the first until scope reclaim and distorting hit-rate/write-amp in spill-heavy runs. Same silent-drop pattern exists for `recompute_persist` when the index is full (`src/engine.rs:212` `.ok()` → unpublishable block written to DRAM/SSD). Fix direction (orchestrator): pass the rolled-back slot through (or re-`insert_pending` after the SSD append) so the SSD copy is published.
2. **Cross-session (shared-prompt) reads are not protected by the D15 reader pin (engine gap).** `get_request` pins only `spec.signals.session` (`src/engine.rs:428`), but hybrid requests resolve blocks owned by the shared-prompt session (`src/replay.rs:167-185`). The shared session is the **oldest** scope (created first, `src/workload.rs:217-231`), hence the first reclaim victim whenever the DRAM watermark trips while it is unpinned; a reclaim between index lookup and the inline arena read (`src/engine.rs:480-489`) can tombstone + free the resolved extent, delivering bytes from a reused offset. The D15 contract ("reader refs pinned at GVA-resolution time" — `src/gva/index.rs:41-47`) requires one pin **per owning scope** (distinct `session` values in `spec.blocks`), not just the requester's. Same-session reads are airtight (pin precedes lookup for that scope).
3. **FlatCake-side metric omissions that break cross-system metric parity (T18):** `requested_blocks` is never incremented by the FlatCake engine (baseline does, `src/baseline.rs:569-656`), so the CSV `requested`/`hit_rate` columns are wrong for FlatCake (`src/replay.rs:283-296`); `logical_read_bytes` is never set anywhere on the FlatCake path (engine merges `io_metrics.logical_read_bytes`, which `cio::stream` never populates — `src/engine.rs:708`, `src/cio/stream.rs:190-191`), so `read_amp` is structurally 0.0 for FlatCake while meaningful for the baseline (`src/baseline.rs:615`); `mem_high_water` and `ssd_over_high_watermark_us` (pinned schema fields, ARCHITECTURE §11) are never recorded by either engine (`track_high_water` has no callers; `ssd_over_high_watermark_us` has no writer). These are measurement-layer gaps, not mechanism deviations — but until fixed, any FlatCake-vs-baseline read_amp comparison is invalid.
4. **Baseline hbm invalidation on lower-tier churn** (`src/baseline.rs:378-381, 425-428, 472-475`) — strict tier semantics (the paper's Fig. 1a) do not evict L1 copies when lower tiers spill or recycle; see Risk R4.
5. **Scheduler conveniences beyond the paper** (documented in-code, benign): `cancel()` removal from queues (`src/mas/scheduler.rs:322-340`), re-admit of an unknown id granting fresh seniority (`:301-307`), post-shutdown enqueue drop. None contradicts a paper mechanism; all are shutdown/robustness plumbing.
6. **Drain-to-low reclamation (D22)** and **writer refs (D15)** exceed the paper's stated protocol — strengthening deviations, recorded in DECISIONS.md, listed here for completeness.

## 5. (3) Level-B vs Level-C statement — hardware boundary, not fidelity gaps

The following are **Level-C hardware capabilities the prototype deliberately does not implement** (design-only in `docs/FUTURE_GDS_INTEGRATION.md`); their absence is not a fidelity finding, and each has a documented Level-B analog in the reviewed code:

1. **GPUDirect Storage / cuFile / `cuFileBatchIOSubmit`, `cuFileHandleRegister`, O_DIRECT on XFS/RAID-0** (paper §4, p. 8) → Level-B: `FILE_FLAG_NO_BUFFERING` positional I/O on NTFS with 4 KiB-aligned offsets/buffers/lengths (OQ-21, D12) — `src/cio/layout.rs:34-37, 144-155`, `src/cio/stream.rs:62-72`, `src/baseline.rs:23, 186-192`.
2. **GPU HBM staging window, CUDA streams, `cudaEventRecord`/`cudaStreamWaitEvent`, GPU scatter kernel into paged KV** (paper §3.4/§4) → Level-B: per-worker two-buffer window with a scoped prefetch thread overlapping the scatter (`src/cio/stream.rs:155-224`); the "consumer" is caller memory; the 8 MiB window is the O(1) stand-in (`src/engine.rs:46-50`).
3. **`cudaMemcpyAsync` H2D for DRAM hits, pinned hugepage DRAM pool (`mmap MAP_HUGETLB`, `cudaHostRegister`)** (paper §4) → Level-B: pre-allocated process-local arena with memcpy semantics under a mutex (`src/gva/arena.rs:63-124`); copy cost inside the lock is a documented Level-B cost (EGM #12).
4. **Register-level transport routing to RDMA / NVMe-oF, multi-node coordinator** (paper §3.2) → Level-B: single node, NodeID=0 (OQ-10); field preserved and tested.
5. **SGLang integration, real model KV tensors, 256-token paged KV scatter, production claude-code-weka-0621 trace** (paper §4/§5.1) → Level-B: `KvEngine` interface + deterministic payload equivalence + synthetic regimes (D3, D17, OQ-18); integrity is *stronger* than the paper's setting (byte-exact verification, `src/replay.rs:105-116`).
6. **Paper-reported numbers (94% hit rate, 1.6× TTFT, 1.000× write amp, etc.)** are the authors' measurements on B200/PM9A3 hardware — never presented as ours (D2); the prototype compares mechanisms qualitatively only.

Everything else reviewed above is **Level-B algorithmic/semantic fidelity**, and the findings in §4 are genuine code-level deviations to fix or measure — not hardware gaps.

## 6. Bottom line

- The five paper mechanisms (GVA encoding + 2^60 partition, publish-after-write, layer-major sort-merge CIO, dual-queue/HRRN/arrival_ts MAS, session-granular reclamation) are implemented faithfully at Level B, with deviations that are documented (D5, D12–D24, OQ-1..21) and defensible, plus two **live engine defects** (§4.1, §4.2) and one **metric-parity defect set** (§4.3) that must be fixed before any benchmark claim.
- The two highest-value measurement guards before M9: (i) the DRAM-hit-share check against the paper's 8.0–11.7% band (Risk R1), and (ii) the baseline staging-collapse onset check (Risk R3). Both can falsify the two biggest interpretations (OQ-19 precedence, baseline strictness) with data instead of argument.
