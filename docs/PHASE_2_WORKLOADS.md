# PHASE_2_WORKLOADS.md — traces, fairness audit, recommended workloads (P2-M4)

Originally assigned to the workload agent; absorbed by the orchestrator after the sub-agent quota was exhausted (ledger incident log). All numbers below are computed from `src/workload.rs` and verified by generation runs.

## Trace format (frozen schema, ARCHITECTURE §11)

JSONL, one record per line: `ts_us, op(put|get), session, turn, layers, start_blk, n_blk, shared, reply_tokens, ctx_tokens, seed, shared_with`.
- Session **1** = globally shared prompt (`shared:1` ⇒ refcount 2 ⇒ DRAM per Table 2 row 1). Real sessions start at 2.
- `shared_with` = session id whose blocks are prepended to a get (hybrid requests, OQ-14).
- Payloads are NEVER stored: bytes are regenerated by the frozen `payload_fill(session, layer, token_start, seed)` and verified byte-exact on every delivery (`src/replay.rs` worker).
- Pacing: `ts_us = (record_index / qps) × 1e6`, open-loop (driver issues at wall-clock `start + ts_us × time_scale`; replay_baseline_tests proves pacing empirically).

## Fairness audit (code evidence)

1. **Identical traces**: `replay::run` consumes the same parsed records for both systems (`src/replay.rs:39-47`); `KvEngine` is the only interface (`src/engine_api.rs:44`). No system-specific trace paths exist.
2. **Identical budgets** (fckv.conf): hbm window 16 MiB both (same code, `src/hbm.rs`); DRAM 64 MiB both (FlatCake pool vs baseline LRU cache — same bytes); SSD 4 GiB both (16×256 MiB scope files vs 128×32 MiB buckets); `recompute_us_per_token` identical (symmetric miss model, D16). The ONLY asymmetric budget is the baseline's 128 MiB staging pool — which is the tiered mechanism itself (paper Obs. 2), documented in BENCHMARK_METHODOLOGY.md's parity table.
3. **Baseline is not weakened**: it implements DRAM-first admission, LRU eviction, promotion on SSD hit (churn), FIFO bucket reclaim invalidating cross-session blocks, staging-pool exhaustion → abort → recompute → re-persist, and NO read coalescing (one physical read per block) — exactly the mechanisms the paper attributes to tiered systems (`src/baseline.rs` header + `advance_or_reclaim`, `StagingPool::reserve`, get SSD arm).
4. **Cold start**: sweep runner wipes only `data/fckv` + `data/baseline` between runs (`benchmarks/run_sweep.sh`); no warm-up (paper §5.1).

Concerns found (reported, not fixed — both are honest mechanism behaviors, not bugs): (a) baseline misses pay only the *modeled* recompute cost (bookkeeping) while FlatCake SSD hits pay real I/O — latency comparisons carry the documented caveat in BENCHMARK_METHODOLOGY.md; (b) A1's R1 risk (OQ-19 DRAM share below the paper's 8–11.7% band) is a workload-shape property to check in M9 results, not a fairness defect.

## Recommended workloads

**Small default (laptop, <2 min)** — the `fckv demo` workload:
```
./target/release/fckv.exe demo
# agentic, 3 sessions x 10 turns, 4 layers, 4 blocks/turn, fanout 1, qps 5
# ≈ 85 records; ~2.5 MiB unique payload; budgets in demo(): 2 MiB DRAM (forced SSD)
```
Observed (evidence, 2026-11-11): baseline 35.32% vs flatcake 82.52% delivered hit rate, integrity_fail=0 both.

**Benchmark sweep (M9, ~60–75 min)**:
```
bash benchmarks/run_sweep.sh
# agentic, 32 sessions x 12 turns, 8 layers, 4 blocks/turn, shared 8, fanout 1
#   unique payload = 32*12*8*4 blocks * 8 KiB = 96 MiB  (> 64 MiB DRAM + 16 MiB hbm)
#   SSD budget check: 96 MiB ≤ 4 GiB ✓;  index: 12,288 unique blocks ≤ 0.7*1,048,576 ✓
#   qps {1,4} x seeds {11,12} x systems {baseline,flatcake} = 8 cold-start runs
```

**Sizing guards** (workload.rs): agentic session bytes ≤ `gpu_file_bytes` (256 MiB) and total put bytes ≤ SSD budget are enforced with explicit errors — never silently truncated.

## Determinism

Same seed ⇒ byte-identical trace file (proven by `matrix_trace_determinism`); seeds flow to per-block payloads via SplitMix64, so integrity verification needs no stored bytes.
